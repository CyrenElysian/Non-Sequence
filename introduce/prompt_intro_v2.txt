# ROLE AND OBJECTIVE

You are an expert annotator of procedural event graphs. You will process a dataset of everyday scripts and output a refined dataset in which every item is logically correct.

Each input item contains:
- "id" (int): item identifier.
- "scenario" (string): the goal of the event chain.
- "unordered_nodes" (dict): node ID -> event description; events are unordered.
- "edges" (list of "A->B" strings): directed edges; "A->B" means event B can directly follow event A in some execution of the script.
- "script_graph" (nested JSON): the event flow described with control-flow primitives.

The input may contain: (1) spelling errors in scenario and unordered_nodes; (2) logical errors in edges (extra edges, missing edges, or wrong edges); (3)logical or structural errors in script graphs (specifically, refer to the following rules); (4) It may only containthe sequence and and-join primitives, so the semantics aren't rich enough.

# CONTROL-FLOW PRIMITIVES

Notation: for an element x, first(x) is its first node ID — first(x) = x if x is a node ID, and first(first_element(x)) if x is a nested structure.

1. sequence: { "type": "sequence", "script": [ ... ] }
   - An ordered list of node IDs and nested structures, executed strictly in order.

2. select: { "type": "select", "options": [ ... ] }
   - Mutually exclusive options: exactly one option is executed.
   - Options must be logically significantly different: the choice must lead to clearly different subsequent events. Trivial differences (e.g., chopsticks vs. spoon for the meal) are not recommended as options. You can refer to the excellent examples in STANDARD EXAMPLES and TRANSFORMATION EXAMPLES below (Example 4, Transformation 3 and so on).
   - Every option must merge into the SAME node that directly follows the select in the enclosing script; each option's last node has an edge to it.
   - There must be no edges between options (they never connect to each other).
   - Each option is a node ID or a nested structure. Every option must be non-empty.
   - Options are unordered; output them in ascending order of first(option). Output "options":["2","3"], not ["3","2"]; output "options":["1",{"type":"sequence","script":["3","2"]}], not [{"type":"sequence","script":["3","2"]},"1"].

3. loop: { "type": "loop", "entry": "...", "retry": [ ... ], "exit": "..." }
   - entry and exit are single node IDs describing concrete events or objective states. Neither may use rigid judgment phrasing such as "decide if", "decide whether", "determine whether", "check if", or "evaluate whether".
   - entry and retry together form the loop body: execution cycles entry -> retry -> entry.
   - retry is an array of node IDs and nested structures; its LAST element must be the literal keyword "continue" (the marker for returning to entry).
   - A direct edge entry -> exit must exist: it is the channel for skipping the loop entirely when the exit condition is met.
   - No node or path inside retry may lead directly to exit.
   - The loop must terminate in principle: each pass through retry must make observable progress toward the exit condition.
   - Node repetition exception: a node may appear exactly twice — once in the surrounding linear context and once inside retry — when the event genuinely recurs. Outside loops, every node appears exactly once.

4. and_join: { "type": "and_join", "branches_set": { "b1": [ ... ], "b2": [ ... ], ... } }
   - Concurrent branches with no temporal or causal order among themselves: they may run in any order, interleaved or even in parallel, but ALL must complete before the merge node.
   - The merge node is the node immediately following the and_join in the enclosing script; every branch's last node has a direct edge to it. The merge node never appears inside branches_set.
   - There must be no edges between branches.
   - Each branch is an ordered list of node IDs and nested structures.
   - Branches are unordered; name them b1, b2, ... in ascending order of first(branch) and output them in that order. Output {"b1":["2"],"b2":["3","1"]}, not {"b1":["3","1"],"b2":["2"]}. With nesting: {"b1":[{"type":"select","options":["1","4"]},"3"],"b2":["2"]} (first 1 < 2); {"b1":[{"type":"and_join","branches_set":{"b1":["1"],"b2":["4"]}},"3"],"b2":["2"]} (1 < 2 and 1 < 4).

# GLOBAL CONSTRAINTS

- Node usage: every node in unordered_nodes appears in script_graph exactly once — except in loop data, where a node may appear exactly twice (see the loop exception).
- Edge consistency (bidirectional): "edges" must contain exactly the edges implied by the script_graph. No missing edges, no extra edges, no dangling nodes or edges.
- Single flow: the graph is one connected control flow; every structure has a unique entry and a unique exit, and a substructure's exit connects to the next node of its parent.
- Do not rename existing node IDs; new nodes take the next unused integer IDs. Do not invent events unrelated to the scenario.

# CONSTRUCTION PROCEDURE

For EVERY item, perform ALL steps in this order in one pass:

Step 1 — Spelling. Fix obvious misspellings in scenario and unordered_nodes without changing the intended meaning. Log as "spelling_fix".

Step 2 — Structure inspection. Decide whether the underlying logic already contains a select or a loop that was mis-annotated as sequence/and_join (words like "repeat", "until", "wait for", "or" are cues, not proof — judge the logic):
   - If yes and it can be expressed correctly by adjusting nodes/edges: restructure it correctly and log "structure_changed". You can refer to the excellent examples in STANDARD EXAMPLES and TRANSFORMATION EXAMPLES below. (Transformation 2, 4 and so on)
   - If yes but a correct restructure is not feasible: the item is an annotation error — remove it from processed_data and log "deletion" with the reason.

Step 3 — Introduction. For the remaining items, consider introducing at least one select, loop, or and_join, possibly by adding a few nodes or making node meanings richer:
   - Imagination is encouraged, but the logic must be natural, never forced. If there is no natural introduction plan, keep the item unchanged.
   - Select: branches mutually exclusive and significantly different; all branches merge to the same following node.
   - Loop: an explicit, observable termination condition; entry/exit wiring as specified above.
   - Delete every old edge invalidated by the restructured control flow; remove any edge that contradicts the new control flow.

Step 4 — Scenario-duplicate end node. Apply the dedicated rule below where relevant.

After generating new edges and script_graph, double-check them TOGETHER using the checklist below.

# ADDITIONAL CORRECTION RULE: SCENARIO-DUPLICATE END NODE

One node in unordered_nodes usually repeats the scenario text and is meant to mark the end of the chain. Using the bare scenario phrase as the final event is often illogical, because the goal may already be achieved before it (e.g., the goal "begin by calling first person on list" is already accomplished once the control flow reaches "wait for answer"; appending the duplicate node afterwards creates an awkward tail). You may either delete that node, or rewrite it into a natural closing event (e.g., "successfully talked with the other party"). Whenever you apply this correction, log it as "structure_changed".

Original:
{"id":738,"scenario":"begin by calling first person on list","unordered_nodes":{"0":"dial number off list","1":"wait for answer","2":"locate a phone","3":"double check list","4":"press call button","5":"make a list","6":"begin by calling first person on list"},"edges":["0->4","1->6","2->0","3->0","4->1","5->3","5->2"],"script_graph":{"type":"sequence","script":["5",{"type":"and_join","branches_set":{"b1":["2"],"b2":["3"]}},"0","4","1","6"]}}

Here node "6" duplicates the scenario and adds nothing after "1". Rewrite it into a coherent closing node (or delete it) and update edges and script_graph accordingly.

# SELF-CHECK CHECKLIST

Before finalizing, verify for every kept item:
[ ] Every node appears exactly once in script_graph (or exactly twice — once inside, once outside a loop).
[ ] "edges" equals the set of edges implied by script_graph: no missing, no extra, no dangling.
[ ] select: options sorted ascending by first node; mutually exclusive; no cross-option edges; all options merge to the same next node.
[ ] loop: entry/exit are concrete event/state nodes without rigid decision phrasing; retry ends with "continue"; an entry->exit edge exists; no path from retry to exit; the cycle returns to entry; completing the entry is compatible with both the retry and the exit; termination is plausible.
[ ] and_join: branches sorted ascending; no cross-branch edges; every branch reaches the merge node; merge node not inside branches_set.
[ ] change_log records every modification (spelling_fix / deletion / structure_changed).

# TRANSFORMATION EXAMPLES (how to convert flat sequences into graphs with select/loop)

Transformation 1: adding a loop to a sequence
Original (flat):

Reasoning: a person browsing neckties on a website is continuously comparing products — a repeating cycle: find a necktie (with mild interest) -> feel dissatisfied -> find another necktie. But instant preference and immediate purchase are also possible: find a necktie -> order the necktie. So we add one node "feel dissatisfied". The entry is "find a necktie", the exit is "order the necktie", the retry is "feel dissatisfied". Entry and exit are single nodes describing specific events or objective states, with no rigid phrasing such as "decide" or "determine whether". A direct path entry -> exit exists (find a necktie -> order the necktie), allowing the process to conclude without looping; and a valid cycle entry -> retry -> entry exists (find a necktie -> feel dissatisfied -> find a necktie).
